summary: EKA-11 (#318) is implemented for the dormant MOD-09 gov.gr Alpha path, based on origin/main b9b3fed. The process-local `_oauth_states` dict in apps/api/routers/govgr.py was the audit finding at line 77-78. It was not TTL-bound, not shared across workers, lost on restart, and consumed with a non-atomic check-then-pop. It has been removed and replaced with the existing shared Redis. No new store, schema, migration, dependency or config key was added. Persistence: the Redis at `REDIS_URL` (compose service `redis`, redis:8.10-alpine), using the same client and URL convention as routers/sso.py. SSO already uses GETDEL for its one-time DiscourseConnect nonces, so the server support for GETDEL is already relied on in production. Issue: `secrets.token_urlsafe(32)` (256 bit). Redis key `govgr:oauth_state:v1:<sha256(state)>` (the raw state is never stored), set with `SET NX EX 600`. On an NX collision the server refuses rather than overwriting. The record binds `purpose=govgr_oauth_login:v1`, `client_id` and `redirect_uri`, plus `redirect_after`, `iat` and `exp`. Consume: first a format check (`^[A-Za-z0-9_-]{43,128}$`, done before any store access), then an atomic `GETDEL`, so exactly one consumer receives the record. Then the embedded `exp` is checked, as a second TTL guard in case the Redis TTL is lost, and purpose, client_id and redirect_uri are compared in constant time. A state whose context does not match is still burned. Fail closed: any store exception on login or callback returns 503, there is no redirect to gov.gr and no token exchange. There is intentionally no in-memory fallback. Invalid, expired, replayed, foreign or corrupt state returns 400 before the provider is contacted. Also removed: the 8-character state prefix from the login log line. The flow stays default OFF: `GOVGR_FLOW_ENABLED` defaults to false, ACTIVATION_GATES are unchanged, and `is_active()` is unchanged.

risks: (a) The state is not bound to the browser session: there is no cookie and no PKCE. An attacker who obtains a victim's unused state within 10 minutes could still attempt login CSRF or session fixation. Browser binding would need a cookie or PKCE verifier, which conflicts with the "no cookies" principle and is a design decision for Sol/Gio. PKCE also depends on gov.gr support, which is undocumented. (b) `redirect_after` is stored and echoed unvalidated (it is returned in JSON, not used for a redirect). It should be restricted to same-origin relative paths before activation; this was out of scope here. (c) The auth URL query parameters are not URL-encoded (pre-existing). (d) The TTL is a code constant (600 s) and not configurable by env, deliberately, to avoid a config change. (e) A Redis flush or eviction invalidates in-flight logins. That is fail-closed and acceptable, but an eviction policy other than noeviction could drop states under memory pressure (UX, not security).
security: Threat model: CSRF or login fixation through a forged or replayed OAuth callback state; replay of a captured state; a race between workers consuming the same state; state that outlives a restart or is split across workers; downgrade to unsafe behaviour when the store is unavailable. Mitigations are as summarized above: 256-bit entropy, TTL enforced in the store and in the record, context binding, atomic single-use GETDEL, and 503 fail-closed with no fallback. New attack surface: Redis keyspace `govgr:oauth_state:v1:*`, holding hashed keys only, no PII and no tokens (the value holds client_id, redirect_uri and redirect_after). Anyone with write access to Redis could mint states; that is the same trust level as the existing SSO nonces. No PII, secrets or gov.gr access in the tests (synthetic `sub`, fake token). DPIA/Alpha boundary: this is hardening of dormant code only.
